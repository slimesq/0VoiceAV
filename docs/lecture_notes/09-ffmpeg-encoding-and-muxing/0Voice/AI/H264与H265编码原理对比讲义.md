## 02 编码标准与编码器实现

| 项目 | H.264 | H.265 |
|---|---|---|
| 常用名称 | AVC | HEVC |
| 英文全称 | Advanced Video Coding | High Efficiency Video Coding |
| 中文名称 | 高级视频编码 | 高效视频编码 |
| 第一版发布时间 | 2003 年 | 2013 年 |
| 常见软件编码器 | x264 | x265 |
| FFmpeg 编码器名称 | `libx264` | `libx265` |
| FFmpeg 编码 ID | `AV_CODEC_ID_H264` | `AV_CODEC_ID_HEVC` |

H.264、H.265 规定码流语法和解码过程。x264、x265 是生成相应码流的编码器实现。标准本身不规定编码器必须怎样搜索运动矢量、尝试多少种模式，也不规定编码一帧必须花多少毫秒。

因此，同一种标准的不同编码器、不同版本和不同参数，可以产生不同的画质、码率与速度。比较“H.264 和 H.265”时，需要明确实际比较的是哪些编码器和配置。

第一版发布时间可核对 [ITU 的 H.264 标准记录](https://www.itu.int/myworkspace/t-rec/item?number=H.264)与 [H.265 标准记录](https://www.itu.int/rec/T-REC-H.265)。这些年份是首版发布时间，不表示标准此后没有更新。

## 03 共同的编码流程

两者都采用基于预测、残差和变换的混合编码框架：

```text
原始图像
   │
   ├── 选择预测方式 ── 帧内预测：使用当前帧中已重建的相邻像素
   │                 帧间预测：使用已重建的参考帧和运动信息
   │
   └── 原始图像 − 预测图像
                │
                ▼
              残差
                │
                ▼
          变换 → 量化 → 熵编码 → 编码码流

编码器内部还会重建图像：
量化系数 → 反量化 → 反变换 → 与预测值相加 → 环路滤波 → 参考图像
```

编码器保存重建图像作为参考，是为了使后续预测与解码器使用相同的图像。普通有损编码中，重建图像与原始图像可能存在量化误差。

举一个简化的像素例子：

```text
原始像素：100
预测像素： 97
残差：      3
```

如果预测改进为 99，残差便变为 1。对一整块图像来说，较准确的预测通常能够减少需要编码的残差信息。不过，预测模式和运动信息本身也要占用比特，编码器会综合比较这些成本。

两种标准的共同框架见 [RFC 7798 的编码工具概述](https://www.rfc-editor.org/rfc/rfc7798#section-1.1.1)。

## 04 主要技术差异速查

| 比较项 | H.264 | H.265 |
|---|---|---|
| 基本块组织 | 以亮度区域为 16×16 的宏块为基础 | 以 CTU 为树根，亮度区域最大为 64×64 |
| 块划分方式 | 宏块内部可继续划分 | 使用四叉树划分 CU，并组织预测与变换单元 |
| 亮度帧内预测 | 4×4、8×8 块各有 9 种模式；16×16 块有 4 种模式，8×8 模式需要相应 Profile | 35 种模式，即 33 种角度模式、DC 模式和平面模式 |
| 常见残差变换尺寸 | 4×4；相应 Profile 可使用 8×8 | 4×4、8×8、16×16、32×32 |
| 熵编码 | CAVLC 或 CABAC，取决于 Profile 和配置 | 改进后的 CABAC |
| 环路滤波 | 去块滤波 | 去块滤波与 SAO |
| 常见参数集 | SPS、PPS | VPS、SPS、PPS |
| NAL 头 | 普通 NAL 头为 1 字节 | NAL 头为 2 字节 |

变换尺寸表列出常见主变换，未展开特殊 DC 变换等情况。两种标准都采用整数化的变换设计，实际处理不能直接等同于任意浮点 DCT 程序。

工具差异可对照 [HEVC 技术概述](https://www.rfc-editor.org/rfc/rfc7798#section-1.1.1)、[H.264 标准](https://www.itu.int/rec/T-REC-H.264-201610-S/en)以及 [HEVC 参考软件说明](https://hevc.hhi.fraunhofer.de/HM-doc/group___t_lib_common.html)。

## 05 从宏块理解 CTU 与编码树

### H.264 的宏块

H.264 的宏块具有 16×16 的亮度区域，并包含与色度格式对应的色度数据。

“宏块是 16×16”描述的是基础组织尺寸。宏块内部仍可使用较小的预测分区和变换块。例如，运动补偿可以针对不同的小区域使用不同运动信息。

因此，宏块尺寸、预测块尺寸和变换块尺寸需要分别理解。

### H.265 的 CTU 与四叉树

CTU 是 Coding Tree Unit，中文为编码树单元。其亮度区域可以配置为 16×16、32×32 或 64×64。

四叉树划分的含义是：一个正方形区域可以保留，也可以划分为四个相同大小的正方形区域，然后分别决定是否继续划分。

下面是教学示意，省略了没有展开的兄弟区域：

```text
一个 64×64 CTU
├── 左上 32×32：保留为较大的 CU
├── 右上 32×32：保留为较大的 CU
├── 左下 32×32：继续划分
│   ├── 16×16
│   ├── 16×16
│   ├── 16×16
│   └── 16×16：还可继续划分为四个 8×8 CU
└── 右下 32×32：保留为较大的 CU
```

如果区域主要是平滑天空，较大的块可能减少块级信息的开销；如果区域包含文字、树叶或复杂边缘，较小的块可能更适合描述局部变化。具体选择由编码器判断，不能预先断言某类画面一定使用某个尺寸。

例如，同一个 64×64 区域，在 H.264 的组织中覆盖 4×4=16 个宏块；HEVC 可以在条件合适时保留一个 64×64 CU，减少部分块级描述。这里比较的是组织与决策的粒度，并不意味着数据量减少为十六分之一。大 CU 内部仍可有残差，其变换也有自己的尺寸限制。

在这里讨论的 HEVC 基本结构中，CU 最小为 8×8；4×4 可能出现在预测或变换层面。不能把“最小变换块为 4×4”写成“最小 CU 为 4×4”。尺寸关系见 [x265 的 CTU 和最小 CU 说明](https://x265.readthedocs.io/en/master/cli.html#mode-decision-analysis)。

### CTU CU PU TU 的职责

| 名称 | 英文全称 | 职责 |
|---|---|---|
| CTU | Coding Tree Unit | 一片区域的编码树根节点 |
| CU | Coding Unit | 编码单元，组织该区域的编码决策 |
| PU | Prediction Unit | 预测单元，组织帧内或帧间预测 |
| TU | Transform Unit | 变换单元，组织残差的变换与量化 |

PU 和 TU 都与 CU 相关，但不是“先把 PU 再切成 TU”的固定串联关系。预测划分与残差变换划分服务于不同任务，也受到各自的语法约束。

还应区分两个最大尺寸：**64×64 是 HEVC 的最大 CTU 亮度区域尺寸，32×32 是这里讨论的最大变换尺寸。** 一个大 CU 的残差可以使用多个较小的 TU。

## 06 帧内预测与帧间预测

### 帧内预测怎样节省数据

帧内预测使用当前帧中已重建的邻近像素，估计当前块。

以一条倾斜的屋顶边缘为例，预测方向越接近边缘方向，预测图像就越可能接近原图。H.265 提供更细的角度选择，使编码器能够更灵活地匹配这些结构。

DC 模式主要利用邻近样本的平均信息；平面模式适合生成较平滑的渐变预测。模式更多也意味着编码器可能需要评估更多候选，不保证每个候选都能改善压缩。

### 帧间预测怎样节省运动信息

两者都支持参考帧、运动矢量和双向预测。H.265 对运动信息复用和预测进行了改进，常见名称有：

- **Merge**：从空间或时间上的邻近关系中构造候选运动信息，减少重复传输。
- **AMVP**：Advanced Motion Vector Prediction，高级运动矢量预测。先得到运动矢量预测值，再传输必要的差值等信息。
- **亚像素插值**：从参考帧生成整数像素之间的预测样本，提高运动补偿精度。

H.264 本身也有运动矢量预测、Skip 和 Direct 等机制。H.265 对这些思想进行了重新组织和扩展，不能把“复用相邻运动信息”全部当作 H.265 独有的概念。

比较运动预测时，要同时考虑两部分：运动信息占多少比特，以及预测后还剩多少残差。[RFC 7798 的运动预测说明](https://www.rfc-editor.org/rfc/rfc7798#section-1.1.1)介绍了这些改进。

## 07 残差变换 量化与熵编码

### 变换的对象通常是残差

帧间编码并不是直接把整幅图像做一次 DCT。通常先预测，再对分块残差进行变换。

变换系数的位置表示对应的空间变化模式，数值表示这种模式在当前残差中的贡献。H.265 允许更大的变换块，能够利用较大范围内的残差相关性；小块仍适合局部变化复杂的区域。

变换尺寸越大并不总是越好，编码器需要同时考虑信号特征、划分信息与计算成本。[x265 的最大 TU 尺寸说明](https://x265.readthedocs.io/en/master/cli.html#cmdoption-max-tu-size)给出了相关配置。

### 量化决定主要的不可逆误差

量化把一部分不同的系数值合并为同一个表示值，部分系数可能变为零。解码时无法从一个量化值精确区分所有原始值，所以普通编码是有损的。

H.265 的效率提升来自预测、划分、变换与编码等多项工具的配合。在相近画质下，这些工具可能让它减少所需码率；在相同码率下，则可能让它更好地保留细节。

两种标准都具有特定条件下的无损编码能力，普通的默认编码设置仍通常是有损编码。不能根据名称中的“高效”推断它采用无损压缩。

### 熵编码继续减少比特

| 缩写 | 英文全称 | 含义 |
|---|---|---|
| CAVLC | Context Adaptive Variable Length Coding | 上下文自适应变长编码 |
| CABAC | Context Adaptive Binary Arithmetic Coding | 上下文自适应二进制算术编码 |

H.264 可使用 CAVLC 或 CABAC；H.265 使用改进后的 CABAC。熵编码根据符号及上下文的统计特点减少表示长度，本身不会再增加图像失真。

## 08 环路滤波与参考图像

块独立处理和量化可能在边界、边缘等位置引入不自然的变化。两者都具有去块滤波；H.265 还加入 SAO。

| 工具 | 英文名称 | 主要作用 |
|---|---|---|
| 去块滤波 | Deblocking Filter | 减轻部分块边界的不自然变化 |
| SAO | Sample Adaptive Offset | 按规则对部分重建样本加上偏移，补偿一部分重建误差 |

这里的“环路”表示：滤波结果还会参与后续参考图像的形成。它既影响显示画质，也可能影响后续帧的预测。

SAO 不能恢复量化时已经丢失的全部信息，也不能简单理解为“给所有像素统一加一个值”。相关工具可参考 [Apple 的 HEVC 编码工具介绍](https://developer.apple.com/videos/play/wwdc2017/513/)。

## 09 压缩效率 码率与文件大小

### 如何理解省一半码率

HEVC 的目标之一是在相近主观画质下大幅降低码率。标准化时期的一项研究，在其测试序列、编码器和评价条件下，得到相对 H.264 平均约 50% 的主观等效码率节省。[编码效率比较研究](https://ieeexplore.ieee.org/document/6317156/)

这不是每个视频都必须达到的固定比例。实际收益会受内容、噪声、颗粒、运动、编码器、速度预设和画质评价方法影响。

| 固定的比较条件 | 主要观察什么 |
|---|---|
| 相近画质 | 谁需要的码率更低 |
| 相同码率 | 谁的重建画质更好 |
| 相同计算时间或实时要求 | 谁能在该计算预算内取得更好的结果 |

H.264 与 H.265 使用相同数字的 CRF 或 QP，不能据此认定画质相同。两种编码器使用同名的 medium 预设，也不代表计算量相同。

### 文件大小计算例

以下数值是教学假设，不是编码器实测结果：

```text
视频时长：60 秒
H.264 达到某个目标画质需要：8 Mb/s
H.265 达到相近目标画质需要：5 Mb/s
忽略音频与封装开销，采用十进制 MB
```

计算如下：

```text
H.264 视频数据量 = 8 × 60 ÷ 8 = 60 MB
H.265 视频数据量 = 5 × 60 ÷ 8 = 37.5 MB

节省比例 = (60 − 37.5) ÷ 60 = 37.5%
```

如果两者都固定为 8 Mb/s，并且时长相同，视频数据量就基本相同，区别主要体现在画质。实际文件还会包含音频、元数据和封装开销。

## 10 计算量 并行处理与延迟

### 编码速度与压缩效率

编码器需要尝试块划分、预测模式、运动信息和变换等候选，再决定如何编码。更充分的搜索通常能够改善压缩效率，也会消耗更多计算资源。

x265 的快速预设会减少部分搜索和分析；慢速预设会尝试更多选择。因此，“H.265 一定比 H.264 慢几倍”缺少必要的比较条件。软件、硬件编码器以及各自的速度设置都应明确。[x265 预设说明](https://x265.readthedocs.io/en/master/presets.html)

### 并行能力

HEVC 提供了便于并行实现的工具，例如 Tiles 和 WPP。

- Tiles 将图像组织成矩形区域，为并行处理提供边界。
- WPP 是 Wavefront Parallel Processing，波前并行处理。不同 CTU 行在满足上方数据依赖后错开推进。

WPP 并不允许所有块完全独立处理。预测和熵编码状态等依赖仍然存在，并行收益也受图像尺寸和任务分布影响。[x265 的线程与 WPP 说明](https://x265.readthedocs.io/en/master/threading.html)

### 延迟与第一帧输出

编码耗时和编码延迟是两个概念：

| 概念 | 例子 |
|---|---|
| 编码耗时 | CPU 实际花多少时间处理一帧 |
| 编码延迟 | 输入帧进入后，经过多少缓存或等待才能取得相应输出 |

B 帧重排、lookahead、帧级线程和编码器队列都可能影响输出延迟。H.264、H.265 都可以配置低延迟工作方式，标准名称不能直接决定延迟高低。

**I 帧本身可以不依赖后续帧进行帧内编码。** 如果 x264 在送入数帧后才返回第一个 I 帧包，需要结合它的输入缓冲与输出策略解释，不能据此说“I 帧必须参考后面的帧”。

结束输入后，FFmpeg 编码程序还需要进入排空流程：发送空帧，再取出尚未返回的 packet。例如，当前项目的编码辅助函数可使用 `encode(codec_ctx, NULL, pkt, outfile)` 进入该流程。接口要求见 [FFmpeg 编解码收发 API](https://ffmpeg.org/doxygen/trunk/group__lavc__encdec.html)。

## 11 分辨率 位深与播放兼容性

### Profile 与 Level

Profile 描述一组编码工具和格式能力；Level 约束分辨率、处理速率、码率等资源范围。

判断设备是否能播放，至少要考虑：

```text
编码标准 + Profile + Level + 位深 + 色度格式 + 分辨率与帧率
```

H.264 可以用于 4K 视频，也有支持 10 bit 的 High 10 Profile。H.265 常见的 Main Profile 支持 8 bit，Main 10 Profile 支持最高 10 bit。某个标准允许一种配置，并不意味着所有对应的硬件解码器都实现了这种配置。

### 位深与 HDR

8 bit 每个分量有 256 个码值，10 bit 每个分量有 1024 个码值。更高位深有利于细腻渐变的表示，但不能仅凭位深判断实际画质。

HDR 还涉及传递函数、色彩描述、可能的元数据以及显示链路。不能把“H.265”“10 bit”和“HDR”直接画等号；把已丢失细节的 8 bit 视频转成 10 bit，也不会自动找回那些细节。

### 播放环境

H.264 的常见配置覆盖了较广泛的旧设备和播放环境。H.265 的具体播放能力取决于操作系统、浏览器、播放器及硬件配置。

做分发方案时，先确定接收端实际支持的配置，再比较带宽和计算成本。具备 H.264 解码能力，不代表自动具备 H.265 解码能力。Profile 能力和浏览器条件可查阅 [MDN 视频编码指南](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Video_codecs)。

## 12 参数集 NAL 与容器

### 两种码流的头部不能直接通用

| 比较项 | H.264 | H.265 |
|---|---|---|
| 常见参数集 | SPS、PPS | VPS、SPS、PPS |
| 普通 NAL 头长度 | 1 字节 | 2 字节 |
| NAL 类型提取 | `nal[0] & 0x1F` | `(nal[0] >> 1) & 0x3F` |

上表的 `nal` 指向 NAL 头的第一个字节，不包括 Annex B 起始码，也不包括长度前缀。读取前必须检查数据边界，HEVC 的完整 NAL 头至少需要两个字节。

VPS 是 Video Parameter Set，视频参数集。迁移 H.264 的解析代码时，既要处理新增的参数集，也要调整 NAL 头与后续语法的解析。[H.264 NAL 结构](https://www.rfc-editor.org/rfc/rfc6184#section-1.3)与 [H.265 NAL 结构](https://www.rfc-editor.org/rfc/rfc7798#section-1.1.4)给出了头部布局。

### 编码格式与容器

MP4、MKV 等是容器；H.264、H.265 是视频编码标准。容器扩展名不能独自说明视频轨采用哪一种编码。修改文件名也不会把 H.264 码流变成 H.265 码流。

从已有 H.264 视频转成 H.265，一般需要解码后重新编码，过程也可能引入新的有损误差；仅重新封装并不会改变视频编码标准。

### 全局头与 extradata

`AV_CODEC_FLAG_GLOBAL_HEADER` 的作用是让支持该方式的编码器把全局头放入 `extradata`。`extradata` 是内存中的配置数据，单独调用 `fwrite(pkt->data, ...)` 不会把它自动保存到文件。

这项机制同时涉及编码器和输出封装，不能简单按“H.264 或 H.265”决定是否设置。对于裸流，需要保证参数集实际出现在接收端可取得的位置；对于 MP4 等容器，应按格式要求把配置交给复用器。

参数集提取、Annex B 与配置记录的区别，以及缺少 SPS/PPS 的排错过程，见 [SPS 与 PPS 实战讲义](D:/CodeRepositories/0VoiceAV/docs/lecture_notes/09-ffmpeg-encoding-and-muxing/0Voice/AI/H264_SPS与PPS解析及流媒体RTC实战讲义.md)。标志定义可核对 [FFmpeg 文档](https://ffmpeg.org/doxygen/trunk/avcodec_8h_source.html#l00316)。

## 13 FFmpeg 对照实验

### 实验前提

准备同一个视频 `input.mp4`，并确保 FFmpeg 构建包含 `libx264` 和 `libx265`。下面只保留第一条视频流，统一为 8 bit 4:2:0 像素格式、最大关键帧间隔 60 帧、最多连续 2 个 B 帧；`2M` 表示目标视频码率 2 Mb/s。若输入位深更高，这组演示会发生位深转换；它用于比较这些统一条件下的输出，不用于保留原始 HDR 能力。

```powershell
ffmpeg -i input.mp4 -map 0:v:0 -an -pix_fmt yuv420p -c:v libx264 -preset medium -g 60 -bf 2 -b:v 2M h264_2m.mp4
ffmpeg -i input.mp4 -map 0:v:0 -an -pix_fmt yuv420p -c:v libx265 -preset medium -g 60 -bf 2 -b:v 2M h265_2m.mp4
```

这组命令用于体验“相同目标码率下的输出差异”。它没有固定两种编码器的计算时间，单次平均码率也可能偏离目标，因此不能单凭文件大小或 medium 名称得出严格性能排名。

比较时记录实际平均码率、处理速度，并对同一画面观察细节、边缘、运动和颗粒。正式评测还需要控制输入格式、关键帧设置、评价方法等条件。

### 查看编码结果

```powershell
ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,profile,pix_fmt,width,height,avg_frame_rate,bit_rate -of default=noprint_wrappers=1 h265_2m.mp4
```

重点观察：

| 字段 | 用途 |
|---|---|
| `codec_name` | 判断视频编码，H.265 常显示为 `hevc` |
| `profile` | 查看所用 Profile |
| `pix_fmt` | 查看像素格式及相关位深、色度信息 |
| `width / height` | 查看分辨率 |
| `avg_frame_rate` | 查看平均帧率描述 |
| `bit_rate` | 查看可获取的视频流码率信息，部分文件可能没有该字段值 |

FFmpeg 对编码器选项的定义见 [libx264 文档](https://ffmpeg.org/ffmpeg-codecs.html#libx264)和 [libx265 文档](https://ffmpeg.org/ffmpeg-codecs.html#libx265)。

项目代码入口为 [视频编码示例 main.c](D:/CodeRepositories/0VoiceAV/voice_av/09-ffmpeg-encoding-and-muxing/02-encode-video/main.c)。迁移编码器时，还需核对像素格式、编码参数和输出格式要求；两个编码器采用相似的 FFmpeg 收发接口，不代表所有私有选项都可直接复用。

## 14 自测题与参考答案

### 自测题

1. H.265 的 CTU 最大为 64×64，是否意味着其变换块最大也是 64×64？
2. H.264 与 H.265 都以 4 Mb/s 编码 120 秒，忽略音频与封装，视频数据量各是多少？
3. 一个 H.265 文件比某个 H.264 文件小，能否只凭这一点认定两者画质相同？
4. 为什么 I 帧可以独立编码，应用程序却可能送入数帧后才收到第一个 I 帧包？
5. 启用 GLOBAL_HEADER 后直接将 packet 写成裸 H.264，播放时报 PPS 不存在，应优先检查什么？
6. 设备支持 H.265 Main，能否据此保证它能播放任意 Main 10、4K、高帧率视频？
7. `x264 CRF 23` 与 `x265 CRF 23` 能否当作相同画质的比较条件？

### 参考答案

1. 不能。CTU 与 TU 的职责不同；这里讨论的 HEVC 最大变换尺寸为 32×32，大 CU 的残差可以使用多个 TU。
2. 两者都约为 `4 × 120 ÷ 8 = 60 MB`。同码率、同时长的视频数据量基本相同。
3. 不能。还需要比较源内容、分辨率、帧率、位深、编码设置和实际画质。
4. I 帧不依赖后续参考帧，但具体编码器可能采用输入缓存、lookahead、重排或线程流水线，推迟开始处理或返回输出。
5. 检查 SPS/PPS 是否在 `extradata` 中，而程序只保存了 packet。随后按裸流或容器的实际要求处理参数集。
6. 不能。还要核对 Profile、Level、位深、分辨率、帧率以及软件和硬件实现能力。
7. 不能。相同数字不是跨编码器的统一画质刻度，应使用实际码率、重建画质和计算成本进行比较。
