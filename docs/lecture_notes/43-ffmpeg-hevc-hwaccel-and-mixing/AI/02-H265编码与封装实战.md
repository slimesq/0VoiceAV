# H.265 编码与封装实战

> 第43节补充讲义 02 · 承接第9章视频编码与 MP4 合成 · FFmpeg 7.1 接口

本讲解决两个问题：怎样把第9章的 H.264 编码流程迁移为 HEVC，怎样让生成的参数集、
时间戳和压缩数据进入正确的输出格式。先复习[第1讲](01-H265-NALU分析与解码.md)中的 NALU 和 Annex B。

## 1 变化主要发生在编码器配置与输出边界

```text
YUV AVFrame → avcodec_send_frame
            → avcodec_receive_packet → HEVC AVPacket
                                      ├─ 按裸流要求输出 → .hevc
                                      └─ muxer处理 → .mp4
```

`send_frame/receive_packet`、帧缓冲区管理、结束排空都继续使用。
需要重新确认的是编码器名称、支持的像素格式、私有参数，以及输出容器对参数集的要求。
`libx265` 负责编码，解码时使用 FFmpeg HEVC decoder；x265 不是 HEVC 解码器。

| 配置 | 学习用起点 | 要理解的含义 |
| --- | --- | --- |
| 编码器 | `libx265` | 在当前链接库中查找具体实现 |
| 像素格式 | `AV_PIX_FMT_YUV420P` | 8位4:2:0；10位应另外确认格式、profile与构建能力 |
| `time_base` | `{1, 25}` | 本例每个 PTS 刻度是1/25秒 |
| `framerate` | `{25, 1}` | 声明帧率，用于编码配置 |
| 输入 `frame->pts` | `0, 1, 2...` | 本例每帧递增一个编码时间基单位 |
| GOP | 25 | 25 fps下约1秒的最大关键帧间隔配置，场景切换等可能提前插入 |

这组 PTS 只适用于本讲固定25 fps、从0开始的输入。转码时应把输入时间戳换算到
编码器时间基，保留真实时间关系；可变帧率不能无条件改成等距序号。

## 2 一个完整的编码器创建函数

以下函数创建8位、25 fps 的软件 HEVC 编码器，成功后由调用方用
`avcodec_free_context()` 释放。`global_header` 来自输出格式的要求。
调用方传入一个用于接收新context的输出指针；本例要求正的偶数宽高。

```c
#include <errno.h>
#include <libavcodec/avcodec.h>
#include <libavutil/dict.h>

static int open_hevc_encoder(AVCodecContext** result, int width, int height,
                             int global_header)
{
    if (!result)
        return AVERROR(EINVAL);
    *result = NULL;
    if (width <= 0 || height <= 0 || width % 2 || height % 2)
        return AVERROR(EINVAL);
    const AVCodec* codec = avcodec_find_encoder_by_name("libx265");
    AVCodecContext* ctx = NULL;
    AVDictionary* options = NULL;
    int ret;
    if (!codec)
        return AVERROR_ENCODER_NOT_FOUND;
    ctx = avcodec_alloc_context3(codec);
    if (!ctx)
        return AVERROR(ENOMEM);
    ctx->width = width;
    ctx->height = height;
    ctx->pix_fmt = AV_PIX_FMT_YUV420P;
    ctx->time_base = (AVRational){1, 25};
    ctx->framerate = (AVRational){25, 1};
    ctx->gop_size = 25;
    ctx->max_b_frames = 0;
    if (global_header)
        ctx->flags |= AV_CODEC_FLAG_GLOBAL_HEADER;

    ret = av_dict_set(&options, "preset", "veryfast", 0);
    if (ret >= 0)
        ret = av_dict_set(&options, "crf", "28", 0);
    if (ret >= 0)
        ret = av_dict_set(&options, "tune", "zerolatency", 0);
    if (ret >= 0)
        ret = avcodec_open2(ctx, codec, &options);
    // Unconsumed options indicate a wrong name or an unsupported option in this build.
    if (ret >= 0 && av_dict_count(options))
        ret = AVERROR_OPTION_NOT_FOUND;
    av_dict_free(&options);
    if (ret < 0)
    {
        avcodec_free_context(&ctx);
        return ret;
    }
    *result = ctx;
    return 0;
}
```

这里选择 CRF，未同时设置目标平均码率。CRF 是质量控制参数，不是28 kb/s。
同名 CRF 数值不能直接跨 x264、x265 或 NVENC 比较画质。

`preset` 在编码速度与压缩效率之间取舍；`tune=zerolatency` 会调整缓冲和分析配置。
即便关闭 B 帧，也不能保证从采集到显示完全没有延迟。
x265 的选项与预设可核对[官方命令行文档](https://x265.readthedocs.io/en/stable/cli.html)和
[预设说明](https://x265.readthedocs.io/en/stable/presets.html)。

## 3 AVFrame 与编码循环

给 frame 设置 `format/width/height` 后，用 `av_frame_get_buffer()` 分配缓冲区。
每次写入前调用 `av_frame_make_writable()`；从紧密排列的 YUV 文件复制到 frame 时，
按平面和 `linesize` 处理，不能假设所有编码帧都紧密排列。

循环遵循下面的状态，而不是“送一帧只收一次”：

```text
准备 frame → send_frame(frame)
              ├─ 成功：循环 receive_packet，处理每个 packet
              └─ EAGAIN：先接收已有输出，然后重试原 frame

receive_packet
  ├─ 成功：写出并 av_packet_unref，再接收
  ├─ EAGAIN：需要更多输入
  └─ EOF：编码器已完成排空

输入结束 → send_frame(NULL) 成功一次 → receive_packet 直到 EOF
```

编码器可能为了 B 帧重排、前向分析、线程调度或硬件流水线缓存输入。
因此，“I帧本身不依赖未来图像”并不意味着实际编码器一定立即返回首个 packet。
给编码器送 NULL 是结束信号，不是普通空白图像，也不能在每帧之后调用。

送NULL本身若返回 `EAGAIN`，先接收已有输出，再重试同一个结束信号。
成功进入排空状态后继续收包直到 `EOF`，不靠等待一段时间或重复送最后一帧触发输出。
`avcodec_flush_buffers()` 用于重置、复用编解码状态，具体行为还受编码器能力约束，
不能替代这里的正常结束流程。可核对本地 `libavcodec/avcodec.h` 的发送接口说明。

## 4 裸流与 MP4 的参数集处理

### 4.1 裸流

裸 HEVC 要让接收端获得 VPS/SPS/PPS 和合适的随机接入数据。
文件中不能只有 slice、却丢掉初始化参数集。编码器 packet 的布局要结合编码器和配置确认；
从 MP4 提取裸流时，可使用 `hevc_mp4toannexb`。

`AV_CODEC_FLAG_GLOBAL_HEADER` 的含义是按编码器支持的方式把全局头放到
`extradata`，不是“只输出I帧”。对本例 x265，在打开编码器后检查 `extradata_size`，
不要在 `avcodec_open2()` 前就期待得到生成后的头信息。

### 4.2 MP4

让 muxer 参与整个输出流程：

```text
avformat_alloc_output_context2 → avformat_new_stream
→ 若 oformat->flags 包含 AVFMT_GLOBALHEADER，设置编码器 GLOBAL_HEADER
→ avcodec_open2 → avcodec_parameters_from_context
→ 设置初始 stream.time_base → 打开输出IO → avformat_write_header
→ 重缩放每个 packet 的时间戳 → av_interleaved_write_frame
→ 排空编码器 → av_write_trailer
```

设置 flag 必须早于打开编码器；从编码器复制 `codecpar` 应在成功打开后进行。
MP4 muxer 会根据编码配置生成相应解码配置记录；`extradata` 的具体字节格式
不能仅凭“它叫 extradata”判断一定是完整 `hvcC`。

`hvc1` 和 `hev1` 是 HEVC 的 MP4 sample entry 类型。先掌握参数集位置的区别：

| 类型 | 本讲关注的参数集约束 |
| --- | --- |
| `hvc1` | 参数集存放在sample description的配置中，不应在媒体sample内携带参数集 |
| `hev1` | 允许在媒体sample内携带参数集，配置组织需符合相应规则 |

本讲使用 `hvc1` 输出例子。Apple的[HLS编写要求](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html)
也区分了sample description和sample中的参数集存储方式。
修改 tag 不能替代正确的参数集组织，也不会把 H.264 转成 HEVC。
具体写入行为可对照[FFmpeg 7.1.3 MOV/MP4 muxer源码](https://github.com/FFmpeg/FFmpeg/blob/n7.1.3/libavformat/movenc.c)。

## 5 两个时间基怎样连接

假设编码器使用 `1/25`，MP4 muxer 在写头后选用了 `1/12800`：

| 实际时间 | 编码器 PTS | MP4轨道 PTS |
| --- | --- | --- |
| 0秒 | 0 | 0 |
| 0.04秒 | 1 | 512 |
| 0.08秒 | 2 | 1024 |

值变了，时间没有变。每个编码 packet 送 muxer 前执行：

```c
// enc、stream、packet 已由上文初始化；这是写包位置的调用片段。
av_packet_rescale_ts(packet, enc->time_base, stream->time_base);
packet->stream_index = stream->index;
ret = av_interleaved_write_frame(output_ctx, packet);
```

检查写包返回值；对于引用计数的packet，`av_interleaved_write_frame()` 会接管该引用，
返回时原packet已被清空，不能继续拿它的旧 `data` 指针使用。
另外，`av_packet_rescale_ts()` 会换算PTS、DTS及有效duration，不会给缺失的时间戳创造真实时间。

以 `avformat_write_header()` 后的实际 `stream->time_base` 为准，不能保存一个旧副本后一直使用。
同一 packet 的 PTS、DTS 使用同一个时间基，二者可有不同数值；不要为了消除 B 帧负 DTS
就把 DTS 强行写成 PTS。没有有效时间戳时，`AV_NOPTS_VALUE` 也不能当作正常时间参与自制运算。

## 6 复用现有示例做实验

项目[第9章视频编码示例](../../../../voice_av/09-ffmpeg-encoding-and-muxing/02-encode-video/main.c)
可以按名称查找编码器，输入尺寸和帧率目前固定为1280×720、25 fps。
当前文件收尾处的 `encode(codec_ctx, frame, pkt, outfile)` 再次送入的是最后一帧，
没有发出结束信号。本次用5帧输入验证，x265 尚在等待后续输入，输出文件为空。
先在学习副本中将收尾调用修正为下面这一句，再编译运行；循环内正常送帧的调用保持不变：

```c
// Input has ended: drain the encoder instead of sending the last frame again.
ret = encode(codec_ctx, NULL, pkt, outfile);
```

`encode()` 内部已有循环收包，因此收到NULL后可以取出缓存结果。
这也是迁移编码器时必须重新验证结束流程的原因。

如果在原示例文件中完成修正，先从仓库根目录重新构建，再运行下面的短输入实验。
如果修改的是独立学习副本，将命令中的可执行文件路径换成副本的构建产物。

```powershell
cmake --build --preset voice-av-vs2022-x64-debug --target voice_av_09_02_encode_video
ffmpeg -y -f lavfi -i "testsrc2=size=1280x720:rate=25" -frames:v 5 -pix_fmt yuv420p -f rawvideo .\voice_av\test_files\43-ffmpeg-hevc-hwaccel-and-mixing\input_1280x720.yuv
.\build\cmake\Debug\voice_av_09_02_encode_video.exe .\voice_av\test_files\43-ffmpeg-hevc-hwaccel-and-mixing\input_1280x720.yuv .\voice_av\test_files\43-ffmpeg-hevc-hwaccel-and-mixing\project.hevc libx265
ffprobe -v error -select_streams v:0 -count_frames -show_entries stream=codec_name,width,height,nb_read_frames -of default=noprint_wrappers=1 .\voice_av\test_files\43-ffmpeg-hevc-hwaccel-and-mixing\project.hevc
```

本练习应保留5/5帧；它与本章其他使用320×180、50帧样片的实验尺寸和长度不同。
这个现有示例用于观察名称切换和基础裸流编码；其 H.264 私有选项分支不会自动变成
x265 专用配置。要实验低延迟、CRF 或 MP4 输出，应明确增加相应配置及 muxer 流程。

在[本章实验目录](../README.md)还可以运行独立命令：

```powershell
ffmpeg -y -i sample_hevc.mp4 -map 0:v:0 -an -c:v libx265 -preset veryfast -crf 28 -tag:v hvc1 reencoded.mp4
ffmpeg -y -i sample_hevc.mp4 -map 0:v:0 -an -c:v libx265 -preset veryfast -tune zerolatency -bf 0 -g 25 -crf 28 -f hevc low_delay.hevc
```

比较实验中要固定分辨率、帧率、输入内容和长度。码率、编码 fps、首帧延迟、文件大小
分别记录；一个指标不能代替其余指标。

## 7 自测与排错

| 现象 | 优先检查 |
| --- | --- |
| 找不到 `libx265` | 当前工具或当前程序链接的库是否包含 x265，二者分开检查 |
| 裸流提示找不到 PPS | 是否启用了 global header，却没有把参数集传给裸流接收端 |
| MP4 中时长或播放速度错误 | 写头后的轨道时间基、编码PTS和写包前的重缩放 |
| 最后几帧不见了 | 编码器是否成功接收NULL，并持续收包直到EOF |
| 改成 HEVC 后画面错乱 | 实际输入尺寸、像素格式、平面偏移和linesize是否匹配 |

练习：分别生成普通配置和低延迟配置，记录50帧输入最终是否都能解码出50帧；
再解释为什么低延迟配置的压缩效率和输出时序可能发生变化。
统计输出帧数可用 `ffprobe -count_frames`，而不是根据编码packet个数估算。
