# H.265 NALU 分析与解码

> 第43节补充讲义 01 · 面向流媒体与 RTC 开发 · FFmpeg 7.1 接口

本讲接在第8章解封装、H.264 NALU 分析和解码之后。学习目标是：看到一段
HEVC 数据时，先判断它怎样划分 NALU、参数集在哪里，再将正确的压缩数据送进解码器。
压缩工具原理可先复习[H.264与H.265对比讲义](../../09-ffmpeg-encoding-and-muxing/0Voice/AI/H264与H265编码原理对比讲义.md)。

## 1 从 H.264 迁移到 H.265

| 项目 | H.264 | H.265 |
| --- | --- | --- |
| 另一名称 | AVC | HEVC，High Efficiency Video Coding |
| FFmpeg 编码标识 | `AV_CODEC_ID_H264` | `AV_CODEC_ID_HEVC` |
| 常用软件编码器 | `libx264` | `libx265` |
| 常用软件解码器名称 | `h264` | `hevc` |
| NALU 头长度 | 1字节 | 2字节 |
| 常用参数集 | SPS、PPS | VPS、SPS、PPS |

HEVC 是视频编码标准。MP4 是容器，NVENC 是硬件编码实现，三者处于不同层次。
一个 MP4 可以装 H.264，也可以装 HEVC；HEVC 既可以由 x265 编码，也可以由硬件编码器生成。

## 2 先分清数据边界

```text
MP4 文件
  └─ 视频轨道
      └─ sample，经解复用后通常对应一个 AVPacket
          └─ 一个或多个 NALU

HEVC 图像
  └─ 一个或多个 slice segment，对应相关 VCL NALU
      └─ 经解码后输出 AVFrame
```

NALU 是 Network Abstraction Layer Unit，即网络抽象层单元。
VCL 是 Video Coding Layer，携带图像编码信息；参数集、SEI 等属于非 VCL 数据。
一幅图像可以有多个 VCL NALU，参数集 NALU 又不对应一幅独立图像。
因此，不能靠“收到一个 NALU”判断“解出一帧”。

同样，`AVPacket` 不是网络包。对常见 MP4 视频，一个 packet 通常包含一个访问单元，
其中可以有多个 NALU；RTP 则可以把一个 NALU 分片到多个网络包，或聚合多个 NALU。
网络接收层必须先按负载格式重组，才能进入解码层。

访问单元是 Access Unit，简称 AU。对本讲的普通单层视频，一个 AU 包含一幅编码图像
对应的 VCL NALU，以及按规范关联的非 VCL NALU。解码器可能缓存、重排图像，因此
“一包通常装一幅图像”也不意味着每次 `send_packet()` 后都立即得到一个 `AVFrame`。

HEVC over RTP 中常见的边界处理如下；这些传输结构定义于
[RFC 7798 第4.4节](https://www.rfc-editor.org/rfc/rfc7798.html#section-4.4)：

| RTP负载结构 | 接收端先做什么 |
| --- | --- |
| 单NAL包 | 按协商的负载格式取出其中的NALU |
| AP，聚合包，Type=48 | 按内部长度字段拆成多个NALU |
| FU，分片单元，Type=49 | 按分片信息重组负载，并恢复原NALU头 |

AP/FU 的 Type 是传输结构标识，不能把它们当作完整图像NALU直接送给解码器。
后文的头解析函数只能识别字段，不能替代这里的拆包和重组。
也不能把一次 socket 读取的数据直接当作完整NALU；重组层应处理不完整数据、乱序和丢失。

## 3 两字节 NALU 头如何解析

下面的位置从字节的最高位开始，左边是先出现的字节：

```text
byte 0                         byte 1
┌─┬────────────┬─┐             ┌──────────┬───────┐
│F│ Type 6 bits│L│             │L 5 bits  │T 3 bits│
└─┴────────────┴─┘             └──────────┴───────┘
  forbidden_zero_bit 1 bit
  nal_unit_type       6 bits
  nuh_layer_id        6 bits，跨越两个字节
  nuh_temporal_id_plus1 3 bits
```

`F` 在有效普通码流中为0。`Type` 表示单元类型；`LayerId` 表示层标识，普通单层流
通常为0；`T` 为时间层编号加1，所以必须非零，真实时间层编号是 `T - 1`。
时间层不是帧率，也不是 PTS。字段定义可核对 [RFC 7798 第1.1.4节](https://www.rfc-editor.org/rfc/rfc7798.html#section-1.1.4)。

以下函数只解析已经切好的一个 NALU 的头。`nal` 必须指向头字节，前面不能包含起始码、
长度字段或 RTP 头；函数不负责切包，也不负责解析 SPS 内容。

```c
#include <stddef.h>
#include <stdint.h>

typedef struct HevcNalHeader
{
    unsigned type;
    unsigned layer_id;
    unsigned temporal_id;
} HevcNalHeader;

static int parse_hevc_nal_header(const uint8_t* nal, size_t size, HevcNalHeader* out)
{
    if (!nal || !out || size < 2 || (nal[0] & 0x80) || !(nal[1] & 0x07))
        return -1;
    out->type = (nal[0] >> 1) & 0x3f;
    out->layer_id = ((nal[0] & 0x01) << 5) | (nal[1] >> 3);
    out->temporal_id = (nal[1] & 0x07) - 1;
    return 0;
}
```

以 `40 01` 为例：`0x40 >> 1 = 32`，所以类型为32，即 VPS；层为0，时间层为0。
H.264 的 `nal[0] & 0x1f` 公式不能用于 HEVC。

| 头字节示例 | Type | 含义 |
| --- | --- | --- |
| `40 01` | 32 | VPS，Video Parameter Set |
| `42 01` | 33 | SPS，Sequence Parameter Set |
| `44 01` | 34 | PPS，Picture Parameter Set |
| `26 01`、`28 01` | 19、20 | 两种 IDR 类型 |
| `2A 01` | 21 | CRA，Clean Random Access |
| `4C 01` | 38 | 填充数据 |
| `4E 01`、`50 01` | 39、40 | 前缀、后缀 SEI |

0～31是 VCL 类型范围，其中包含保留项。具体枚举可查看
[FFmpeg 7.1.3 的 HEVC 类型定义](https://raw.githubusercontent.com/FFmpeg/FFmpeg/n7.1.3/libavcodec/hevc/hevc.h)。

## 4 Annex B 与长度前缀

同一个 NALU 可以采用不同的外部划分方式：

```text
Annex B，常见于 HEVC 裸流和 MPEG-TS：
00 00 00 01 | 40 01 ... | 00 00 01 | 42 01 ...
  起始码       VPS        起始码      SPS

MP4 sample 中常见的长度前缀方式：
00 00 00 18 | 40 01 ...共24字节 | 00 00 00 2A | 42 01 ...共42字节
  NAL长度                           下一NAL长度
```

上例长度字段是4字节大端数；实际字段宽度由 HEVC 解码配置记录决定，不能对所有
MP4 都硬编码成4。MP4 中通常还通过 `hvcC` 保存解码配置信息和参数集。
`hvcC`、`AVCodecParameters.extradata`、码流中的 VPS/SPS/PPS 有关联，但不是
可以直接互换名称的同一个结构。

起始码和长度字段都在 NALU 头外面；只检查 NALU 头时，先去掉对应的外层边界。
进一步逐位解析参数集时，还需按规范处理防竞争字节，将 EBSP 转为 RBSP，
不能把 NALU 负载中所有 `03` 字节直接删除。

RBSP 是 Raw Byte Sequence Payload，即语法解析使用的原始负载；EBSP 是加入防竞争
字节后的表示。例如按规定插入的 `00 00 03 01`，去掉该防竞争字节后还原为
`00 00 01`。这个步骤处理的是NALU负载，不能连同两字节NALU头一起套用删除规则。

FFmpeg 的 `hevc_mp4toannexb` 做长度前缀到 Annex B 的转换，并处理相应参数集。
它是比特流过滤器，工作对象是压缩数据，不会把视频解码成像素。
可对照本地源码 `third_party/ffmpeg-src/doc/bitstream_filters.texi` 的同名章节及
[官方说明](https://ffmpeg.org/ffmpeg-bitstream-filters.html#hevc_005fmp4toannexb)。

## 5 参数集与随机接入

解码 slice header 时，需要找到它引用的 PPS，再沿引用找到 SPS 和 VPS：

```text
slice → PPS ID → PPS → SPS ID → SPS → VPS ID → VPS
```

可以先理解为：VPS 描述视频层次等总体信息，SPS 描述序列的尺寸、编码结构等，
PPS 描述图像相关的编码配置。完整字段比这里更丰富，RTC 初学阶段先掌握依赖链和更新时机。

播放器中途加入流时，需要可用的参数集和合适的随机接入图像。
IDR 是 Instantaneous Decoding Refresh，即即时解码刷新；它提供不再依赖接入点之前
图像的刷新边界。CRA 也允许随机接入，但其关联的部分前导图像可能仍依赖接入前的图像。
这些前导图像在解码顺序上位于CRA之后，在显示顺序上却位于CRA之前。
从CRA开始接入时，关联的 RASL 图像通常需要丢弃，不能把它们当作普通后续图像播放。
相关区分见 [RFC 7798 的随机接入说明](https://www.rfc-editor.org/rfc/rfc7798.html#section-1.1.2)。

“I图像”“IDR”“关键帧标记”不能直接画等号；仅看到帧内编码，也不足以确认可以任意切流。

流媒体接收端至少要处理三件事：

1. 按参数集种类和ID分别保存、更新，不能把重复接收当作解析错误；VPS、SPS、PPS各自的ID空间不能混成一张只按数字查找的表。
2. 参数集变化导致分辨率等配置变化时，重新评估解码器、滤镜和硬件表面池。
3. 丢包或刚加入时，等待可恢复的访问单元；缺少 PPS 时反复送后续 slice 通常不能自行恢复。

## 6 FFmpeg 解码流程怎样复用第8章

**输入为 MP4 时**，采用 `avformat` 解封装：

```text
avformat_open_input → avformat_find_stream_info → 选视频 AVStream
→ avcodec_parameters_to_context → pkt_timebase = stream.time_base
→ avcodec_open2 → av_read_frame → send_packet → 循环 receive_frame
```

`avcodec_parameters_to_context()` 会复制解码配置，包括 `extradata`。
给 FFmpeg 的 HEVC 解码器送 MP4 解复用得到的 packet，一般不需要先手工转 Annex B。
转换主要用于导出裸流、某些传输接口等明确要求 Annex B 的边界。

解码时间戳要沿输入 packet 的时间基解释；不要因为视频25 fps，就把输入 PTS 直接当成
`1/25`。原时间基为 `1/12800` 时，相邻 PTS 差512，也仍然是25 fps。

**输入为原始字节流时**，需要处理读取边界与编码访问单元边界不同的问题。
可使用 HEVC parser 整理数据，再调用 send/receive；读文件时保留
`AV_INPUT_BUFFER_PADDING_SIZE` 的零填充，结束时排空 parser 和解码器。

项目[第8章视频解码示例](../../../../voice_av/08-ffmpeg-demuxing-and-decoding/06-decode-video/main.c)
已经演示 parser。它当前按文件名选择 H.264/MJPEG，**不能直接给它传 HEVC 并期待自动支持**。
练习改造时，需要同时增加 HEVC 的类型识别和 `AV_CODEC_ID_HEVC` parser/decoder 分支，
只改输入文件后缀或输出文件名不够。

## 7 动手观察

先按[本章入口](../README.md)创建实验目录并生成 `sample_hevc.mp4`。
以下命令均在该实验目录执行：

```powershell
ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,profile,width,height,pix_fmt,time_base,extradata_size -of default=noprint_wrappers=1 sample_hevc.mp4
ffmpeg -y -i sample_hevc.mp4 -map 0:v:0 -c:v copy -bsf:v hevc_mp4toannexb -f hevc sample.hevc
ffmpeg -loglevel trace -i sample_hevc.mp4 -map 0:v:0 -c:v copy -bsf:v trace_headers -f null - 2> hevc_headers.log
Select-String -Path hevc_headers.log -Pattern 'nal_unit_type|vps_video_parameter_set_id|sps_seq_parameter_set_id|pps_pic_parameter_set_id'
ffmpeg -y -i sample_hevc.mp4 -map 0:v:0 -pix_fmt yuv420p -f rawvideo decoded_320x180.yuv
```

实验输入为2秒、25 fps，解码应得到50帧，YUV420P 文件大小为：

```text
320 × 180 × 3/2 × 50 = 4,320,000 字节
```

`trace_headers` 的日志中会出现参数集和不同类型的 slice；一次输出中的 NALU 数量
不必等于50。若当前工具没有该比特流过滤器，用 `ffmpeg -bsfs` 检查构建能力。

## 8 自测

1. `42 01` 对应哪种参数集？为什么不能拿首字节与 `0x1f` 相与？
2. 已知一个 MP4 packet 内有3个 NALU，它是否一定对应3帧？
3. 解码报缺少 PPS 时，最先检查哪些数据和初始化步骤？
4. MP4 转 HEVC 裸流时，为什么 `-c:v copy` 仍可能改变输出字节布局？
5. RTP的FU负载能否原样作为一个完整HEVC NALU送给解码器？

参考答案：分别是 SPS；NALU 与图像没有一一对应关系；检查参数集是否完整、
`codecpar` 是否复制、边界是否正确以及是否从可随机接入处开始；stream copy
不重编码，但比特流过滤器可以调整压缩数据的封装方式。
第5题不能：应先重组分片、恢复原NALU头，再按解码输入要求组织数据。
